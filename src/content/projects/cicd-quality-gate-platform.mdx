## The problem

Before this pipeline existed, shipping a change meant manual release steps threaded through
dev, QA, and prod — the kind of process that works until someone's out sick or a step gets
skipped under deadline pressure. Code quality and security scanning weren't consistently
enforced, so issues that should have been caught pre-merge were instead caught in production,
or not at all.

**Constraints:**
- The pipeline had to serve multiple concurrent programs with different release cadences
  without becoming a bottleneck.
- Quality gates needed to be strict enough to matter (not rubber-stamp checks) but fast enough
  that engineers wouldn't route around them.

As the pipeline's owner, I built Jenkins pipelines to drive the build-and-deploy flow, with
Terraform handling infrastructure as code so environments are provisioned consistently rather
than hand-configured. Every change passes through formatting (Black/Pylint), static analysis
and security scanning (SonarQube, Bandit), and a minimum 80% test coverage gate via pytest
before it can move from dev toward QA and production.

## Key decisions

- **Infrastructure as code, not runbooks.** Terraform-managed environments meant dev, QA, and
  prod stayed configuration-consistent by construction, instead of drifting apart through
  manual changes over time.
- **Gates enforced in CI, not in code review.** Putting SonarQube, Bandit, and coverage
  thresholds into the pipeline itself — rather than relying on reviewers to catch issues —
  made quality enforcement consistent regardless of who was reviewing that week.
- **One pipeline, three concurrent programs.** Standardizing a single dev→QA→prod flow across
  every program running on the platform meant one investment in pipeline quality paid off
  everywhere, instead of three teams maintaining three release processes.

## Outcome

A standardized multi-environment pipeline with manual release steps removed entirely, raised
baseline code quality across the platform, and security vulnerabilities caught before merge
rather than after deployment.
